# Research Slides - 两页沟通胶片提纲

## 触发方式
`/research-slides [<topic_dir>]`（不传则自动定位当前工作目录下的 `*/outline.yaml`）

## 用途与产物
把已完成的调研成果（`results/<slug>.json`）**逐个对象**转成**一页讲业务、一页讲技术**的宣讲提纲，用于：
- 走访/访谈前的沟通准备（让对方看到"我理解你的痛点，也带来了方案"）
- 争取资源与政策支持（如高校向政府/资助方争取算力投入）
- 多对象横向汇报（各对象提纲要能并列、口径能对上）

**产物**：
```
{topic_dir}/slides/
  ├── _TEMPLATE_{语境}两页PPT提纲.md   # 统一模板（子代理讀此檔，主控不寫長 prompt）
  ├── <slug>_两页PPT提纲.md  × N       # 每對象一份
  └── INDEX_交付索引.md                # 索引 + 引用前必讀口徑
{topic_dir}/DATA_QUALITY_NOTES.md       # 主控側數據核驗與口徑裁定（本 skill 的關鍵副產物）
{topic_dir}/qa_slides.py                # 引用紀律 QA（可複跑）
```

## DSH 工具映射
- 詢問用戶 → `ask_user_question`；聯網檢索 → `web_search`；抓網頁/PDF → `bash`(curl)
- 啟動子代理 → `subagent`（**後台**，每對象一個）；文件讀寫 → `read`/`write`/`glob`；命令 → `bash`

---

## 核心原則（先讀）

1. **兩頁的分工是固定的，但語義要隨對象類型翻譯**——見 `SLIDE_SPEC_enterprise.md` / `SLIDE_SPEC_academic.md`。**不要把企業版的「產品／收入」措辭套到高校上，也不要為輕算力對象虛構需求。**
2. **主控做「核驗、口徑、QA、索引」；子代理做「敘事」**。主控**不**替子代理寫提綱內容，子代理**不**自行決定跨對象口徑。
3. **引用紀律是本 skill 的硬底線**：每個 `[S#]` 必須指向**真實存在**的落盤檔。**寧可少寫引用鍵，不可虛構檔名。**
4. **口徑必須聲明範圍**：凡「全市場／全機構／全澳」等匯總數字，**必須寫明它包含哪些對象、不含哪些**（實戰中同一份報告的匯總數與明細行常不同範圍）。

## Step 0：定位與前置檢查

```bash
# 1) 定位 topic_dir 與對象清單
ls */outline.yaml
python3 - <<'PY'
import yaml,json,os
o=yaml.safe_load(open('{topic_dir}/outline.yaml'))
items=o.get('items',[])
print("對象數:",len(items))
for it in items:
    slug=it.get('slug')
    p=f"{topic_dir}/results/{slug}.json"
    print(f"  {it.get('name')} | slug={slug} | result={'OK' if os.path.isfile(p) else 'MISSING'}")
PY
```

**前置條件**：每個對象須有 `results/<slug>.json`（由 `/research-deep` 產出）。缺失者先補做，或在提綱中明示缺口——**不得以推測內容填充**。

用 `ask_user_question` 確認：① 對象清單（是否含橫向專題）；② 語境（企業／高校機構／混合）；③ 兩頁的宣講對象與目的（決定 Slide 2 的落腳點是"要多少"還是"怎麼給"）。

---

## Step 1：判定語境並選模板骨架

| 語境 | 模板 | 典型對象 |
|---|---|---|
| **企業版** | `SLIDE_SPEC_enterprise.md` | 公司、廠商、平台方 |
| **高校／科研機構版** | `SLIDE_SPEC_academic.md` | 大學、學院、研究院、智庫 |
| **橫向專題** | 借用最接近者並**改寫語義** | 「其他科研機構」「政策與基建生態」等非單一主體對象 |

混合場景（如"14 家企業 + 2 個橫向專題"）**統一用一套模板**，僅對橫向專題調整語義。

---

## Step 2：寫統一模板（**本 skill 效率的關鍵**）

把兩頁規格、五要素、口徑聲明、引文紀律、〈待驗項〉格式、自檢腳本**一次寫進** `slides/_TEMPLATE_*.md`。

此後每個子代理的 brief 只需三行：「讀模板 → 讀你的 `results/<slug>.json` + 算力/數據源 → 照做並跑自檢」。
**不要**在每個子代理 prompt 裡重複貼兩頁規格——既浪費又會在各份之間產生漂移。

模板必須包含（缺一不可）：
- 兩頁標題格式與內容結構（逐條列出）
- 五要素定義（角色／替代哪段人力／閉環／工具·API／護欄）
- **口徑聲明**（該領域的統一計量口徑）
- 引文紀律（證據分級、不得編造、術語用「」）
- 〈待驗項〉表格式
- 引用鍵對照表格式 + **硬性要求「被引檔必須存在」**
- **完成前自檢腳本**（見 Step 4 的 `qa_slides.py`）

---

## Step 3：主控側前置數據核驗（**兩次實戰最大的教訓，不可跳過**）

**在派發子代理之前**，主控必須自己核驗數據基座，並把結論寫成 `DATA_QUALITY_NOTES.md`。原因：**子代理會發現這些矛盾並停下來問你**；先查清可省下大量往返，也避免錯誤被寫進多份提綱。

必查五項：

1. **範圍口徑**：匯總數字與明細行是否同範圍？（實例：報告匯總表寫「合計 92 單位」，但其表格只列 12 個對象、行合計 82——**是範圍差，不是錯**；必須寫明）
2. **「看似分級、實則不然」的標籤**：任何 `tier`／`level`／`grade` 類欄位，**先驗證它是否與數量指標單調相關**。實例：某專案的 `tier=T1_旗艦重算力` 卻只對應 2,244 單位（另一對象 10 個 T1 單位合計 239,417，平均 23,942）——**該標籤是按性質標註而非規模分級，不可作規模判據**。
3. **區間 vs 點值**：明細給區間、模型給點值時，逐個核驗點值是否落於區間內；**若越界，判定是「取上界」「口徑不同」還是「數據缺陷」**。
4. **欄位可信度**：抽樣比對 `constraints`／`partners`／`bottleneck` 等欄位與該對象的主業／研究方向是否相符——**實戰中出現過整段複製錯位**。
5. **合規衝突**：`results` 中若有「建議使用外部 API／雲服務」類欄位，**與該對象的敏感資料描述對照**；涉及健康/遺傳/個人敏感資料者，**合規約束優先於該建議**（實例：某檔建議用商用 LLM API 做質性編碼，但同檔載明訪談涉健康與性生活內容）。

`DATA_QUALITY_NOTES.md` 應含：口徑裁定、已知缺陷（**標明「未修改既有數據檔，以本說明為準」**）、易誤讀表述、以及**給子代理的硬性規則**（見 Step 5）。

---

## Step 4：建 QA 腳本（複製 `qa_slides.py` 到工作區並改對象清單）

把本 skill 的 `qa_slides.py` 複製到工作區，改 `ENTITIES` 清單即可。它核驗：

- Slide 1／Slide 2 結構、〈待驗項〉表、引用鍵對照表
- **引用鍵雙向對齊**（正文用 ↔ 表定義）
- **被引檔逐檔存在於 `sources/`**（遞迴索引，支援中文檔名與 `results/` 中間檔）
- 量化要素、口徑聲明、核心結論

**驗收標準：`qa_slides.py` 輸出「有錯誤：無」。**

> ⚠️ **本腳本自身有過三次假陽性，改寫時注意**（詳見 `PITFALLS.md`）：非遞迴索引、ASCII-only 檔名正則、多檔名 evidence 字串；另有「〈待驗項〉編號被誤判為引用鍵」。

---

## Step 5：分批派發子代理（每對象一個，後台）

**每批 6–7 個**，避免一次開太多。每個 brief 的固定結構：

```
目標：為 **<對象名>**（slug: `<slug>`）產出兩頁 PPT 提綱。<一句話語境/定位>

## 第一步（強制，依序完成）
1. read `slides/_TEMPLATE_*.md` 全文——統一規格，必須嚴格遵循，不得自創結構
2. read `results/<slug>.json` 全文
3. bash 讀取 <算力/數據源> 中屬於本對象的條目——**數字一律以此為準，不得自行編造或推估**
4. read <總報告> 的 TL;DR／相關章節，作為跨對象共用事實的引用來源
5. bash 確認引用鍵目標檔存在：`ls sources/<該對象來源目錄>/`

## 交付
`slides/<slug>_两页PPT提纲.md`，約 <N>–<M> 行。

## 本家要點（<對象> 的特殊性，務必體現）
<3–6 條該對象獨有的、必須寫進去的實質內容與論證方向>

## 硬性要求
- Slide 1：<板塊數> 個板塊<選取依據>，每條給「<三要素>」，頁末 `> **核心結論**：`
- Slide 2：(1) **三大 AI/Agent 應用構想**，每條五要素齊備（護欄必須含 <該領域的合規要點>）；
  (2) <算力/資源>需求分層評估 <表/架構>，頁末 `> **核心結論**：`
- 〈待驗項〉<n>–<m> 條，素材取自 `uncertain[]` 與各單位 `uncertainty_notes`，逐條給「表述｜現有證據｜降級寫法」
- 引用鍵指向 `sources/` 內**真實存在**的檔案；跨對象共用源須在對照表明示
- **完成前必須執行模板第七節自檢腳本**，確認「被引檔不存在：NONE」
- 不得編造；所有估算與構想標明為推論

## 回報（簡短）
交付路徑｜檔案大小｜引用鍵數｜被引檔是否全部存在｜Slide1 板塊數｜Slide2 構想數｜待驗項條數｜
**任何與 `results/<slug>.json` 不符、或你認為需要主控注意之處**
```

**要點**：
- 「本家要點」是**質量分水嶺**——它讓每份提綱有辨識度，避免 N 份長得一樣。
- 對**輕量對象**要**明確反向指示**：「不要虛構需求，論證應是『以共享為主、無需專項投入』」。
- 結尾那句「需主控注意之處」是**關鍵的信息回流機制**——子代理會藉此報回數據矛盾。

---

## Step 6：主控側核驗與**通報回路**（時間敏感）

子代理會陸續回報「與 `results/*.json` 不符」之處。主控須：

1. **逐項獨立核驗**（不要直接採信轉述——實戰中子代理的「矛盾」常是**比較基準不同**或**解析假象**所致）；
2. 若確為缺陷，**追加到 `DATA_QUALITY_NOTES.md`**；
3. **立即 `send_message` 通報仍在運行的子代理**——它們可能正要用到該欄位；
4. **隨時準備更正自己**：實戰中主控的 brief 曾有 ①對象排名寫反、②把「某標籤單位小計」誤寫成「全校總值」——**均由子代理發現並糾正**。收到糾正後，**必須回頭更正已發給其他子代理的同類表述**。

---

## Step 7：驗收與索引

```bash
python3 qa_slides.py          # 必須「有錯誤：無」
```

生成 `slides/INDEX_交付索引.md`，含：
- 逐對象一覽（**只放可機器可靠提取的欄位**：引用鍵數、檔案大小、關鍵量化值）
- **引用前必讀的口徑條目**（範圍聲明、已知缺陷、合規優先級）
- **建議宣講串場詞**（哪些對象同組、如何對比）

> ⚠️ **不要為了「看起來完整」而放不可靠的派生數字**。實戰中曾試圖自動統計「Slide 1 板塊數」，因各份編號格式不一而產出錯數字——**最終改為不放該欄，並註明「請逕閱原檔」**。索引裡的錯數字比沒有數字更糟。

## Step 8：追補缺件

逐項核對交付清單，對缺件者**再派一次**（brief 內明確「你已完成 X，缺 Y，請只補 Y 以免覆蓋」）。
若某對象的子代理長期未交付，主控可**依其已落盤來源自行合成**，但**必須在檔案與回報中明示「由主控合成」**（實戰中發生過一次）。
